# v0.10.0 — the locus: an agent's time gets its second ordering

**Breaking, and it requires a migration.** This release changes the shape of the
process layer — the largest such change since the encounter chain itself — and
your existing history does not move itself. Read *Upgrading* below before you
deploy.

## What changed, and why it is not a refactor

An agent's memory had one ordering: `NEXT_ENCOUNTER`, the chain of work units.
That was not enough, and the reason is structural rather than cosmetic.

A human has one beam of time — session and day are the same line, so nothing
forks. An agent does not. Several instantiations of it can be alive at once,
their lifetimes overlapping, each doing its own work. With one chain, there was
no way to say which encounters belonged to the same continuous self, so
succession edges could be drawn between encounters that no single self ever
spanned.

v0.10.0 gives that second coordinate a node. A **`Locus`** is one instantiation,
keyed by the harness session id:

- **`NEXT_LOCUS`** orders instantiations by their genesis. Lifetimes overlap and
  cannot be ordered; a genesis is a *point*, and points order totally because
  the advance is a serialized write.
- **`NEXT_ENCOUNTER`** orders work units **inside** one locus, and never crosses
  between them.
- **`OPENED`** is membership — exactly one locus per encounter.

Two encounters in different loci are **incomparable**. Not "unknown order":
incomparable, because no self spanned them. Locating a point in the agent's time
now takes two coordinates.

**What this fixes for you.** The locus used to be the transport session, held in
server memory. A restart emptied it, so the next advance started a fresh chain
that looked — in the graph — exactly like a genuinely new existence. Restarting
the container and the agent beginning a new life were structurally the same
event, and nothing recorded which had happened. The locus is now a node keyed by
an identity that survives a restart and a `/resume`.

## Breaking changes

| | |
|---|---|
| `advance_encounter` | takes `session_id` (the harness session id) instead of a predecessor. The locus, the chain tail and where the encounter attaches are all derived from the graph. |
| `close_encounter` | takes `session_id`; addresses **your** locus's open tail, resolved from the graph. A parallel sibling can no longer capture your seal. |
| `create_entities` | takes `session_id`; anchors to **your** locus's open encounter, never the global tail. |
| `infuse` | takes `session_id` (optional, additive). Keys the renewal ledger. |
| encounter-name write handle | **removed.** It could address any encounter, including another locus's. It existed only because server state could be lost, which can no longer happen. |
| `INSTANTIATED_AFTER` | **retired.** It encoded a locus-level relation between *encounters*, because loci had no node of their own. Existing edges remain; nothing writes them. |
| `dissolved_at` | **retired.** It marked "the server lost this locus's state" — an event that can no longer occur. Existing values are kept as a record; nothing computes it. |
| `t_sealed` | **new**, and it means something else: an *elected* Stop. |

**Without a `session_id`** the server mints an **anonymous** locus. That is
honest and it works — but it cannot be rejoined after a restart, and it is
flagged `anonymous: true` rather than guessed at. The reference hook supplies
the id for you.

**On `t_sealed`.** An encounter carrying no seal is one whose *ending was never
examined* — the honest record. Conversations stop; they are not closed by
ritual. An unsealed encounter is never given a fabricated summary, and nothing
external can strand one.

## Upgrading — run the migration

Your v0.9.0 encounters have no locus. After the upgrade they are still in the
graph, still correct, and no longer reachable from the layer the agent re-enters
through — with no error, because nothing is broken, only detached.

The server tells you: at startup it counts encounters belonging to no locus and
names the remedy, and the same count rides the re-entry payload the agent reads
before examining anything.

```bash
docker exec kenning_encounter-mcp python -m kenning_encounter.migrate --apply
```

Without `--apply` it reports and writes nothing. **It only ever adds** — there
is no `--reverse`, because nothing in this substrate is deleted and a script
reaching past the tools' own refusal to remove spine nodes would be doing
unsupervised the one thing they forbid. Check-then-write: it refuses before
writing if the graph is not what it expects, and on a post-apply mismatch it
reports and stops rather than undoing anything. Every write is a `MERGE`, so
re-running is a no-op and correcting is forward.

The migration derives `NEXT_LOCUS` from **genesis order**, not from the old
`INSTANTIATED_AFTER` edges. That is deliberate: those edges are injective at the
encounter level but fork at the locus level, because several loci can each begin
at different points inside one predecessor's lifetime. Correct data; not a
chain.

**If you deploy without a shell into the container**, an operator has to run
this. It is not exposed as an MCP tool on purpose: a graph-wide write on an
agent's accumulated experience is something a person performs and watches, not
something a container does on boot while nobody is looking.

## If you ran v0.9.0 without a `GEMINI_API_KEY`

The meaning-sidecar reconcile sweep logged a node's **name** each time
compression was unavailable — once per node, so a keyless first start wrote the
whole graph's names to container stdout. In this substrate a node's name *is*
content rather than a label, so those logs read as an index of what the agent
holds, in a file carrying none of the database's credentials.

v0.10.0 logs shape only: counts and distinct reasons, never names, enforced by a
helper whose signature has no parameter a node can arrive through. The search
tool logs its query *length*; name lookup logs a *count*. If you ran v0.9.0
keyless, treat the existing container logs as sensitive and rotate or clear
them.

## Also in this release

- **The unsealed set names its locus.** `orient` and the re-entry payload report,
  for each encounter with no seal, which `Locus` opened it and whether that locus
  is anonymous. An anonymous locus can never be resolved to again, so its
  unsealed encounters are over whatever ended them; a named one could still be
  live. It reports the fact and does not render the verdict — the graph cannot
  tell a live sibling from a finished one, and does not pretend to.
- **One definition of a seal.** Sealed means no `t_sealed`, no summary, no
  report — one predicate, consulted by both the write-target resolver and the
  unsealed set, so the two cannot disagree. The union spans both eras: seals
  written before `t_sealed` existed were no less elected, and your pre-upgrade
  encounters keep reading as sealed.
- **Infusion stops repeating itself after a restart.** The renewal ledger is now
  keyed on the durable session id, so material already delivered into a
  conversation stays delivered across a server restart or a transport reconnect
  instead of arriving again at full weight.
- **The process layer stays out of the meaning index.** `Locus` nodes are
  excluded from the sidecar sweep, so they consume no compression calls and never
  compete with real material during seed selection.
- **Infusion arrives on one channel, by construction.** Infusion is a *conflux*
  operation — it has content only where two frames meet — so it arrives on a
  written prompt and never on a tool return. The `mode` parameter and the
  per-tool-batch `delta` channel are gone. A surprising tool return is a reason
  to invoke inside the one frame, not an ambient channel. Silence remains a valid
  injection.
- **A `Locus.session_id` uniqueness constraint** plus an in-query write lock on
  the genesis locus close the mint race; multiple anonymous loci remain permitted.

## Requirements

Unchanged and worth restating: **this requires the Claude Code harness.** Point

constitution — no infusion, no trajectory, no durable locus, and nothing telling
you those are absent. See *Requirements* in the README.
