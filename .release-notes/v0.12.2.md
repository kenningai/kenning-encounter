# v0.12.2 — a degraded infusion tells you so

The infusion hook now tells you, and the trajectory, when an infusion arrives
degraded, instead of failing silently. It also fixes the hook against a
server running stateless. No ontology or configuration changes.

## Fixed: the hook against a stateless server

With `NEO4J_MCP_SERVER_STATELESS=true` (opt-in since v0.12.0), the server
answers the hook's `initialize` with no `Mcp-Session-Id`, which is correct for
a stateless server. The hook treated the missing id as a failed handshake and
never made the `infuse` call. So a stateless deployment ran with no infusion
on any prompt, and nothing said so.

The hook now accepts a missing session id and makes the call without one.
Continuity was never carried by the transport session; the hook sends the
harness session id as `session_id` either way. Stateful servers behave as
before.

**Upgrading:** replace your copy of
`scripts/kenning_encounter_infuse_hook.py`. The hook runs on the host, so
this part needs no server redeploy.

## New: degraded infusion is announced

A trajectory cannot notice its own infusion thinning. A poorer context simply
becomes its whole context. You can often tell from how it answers, but only
after a while. The hook sees every call's outcome, so it now reports a
degraded infusion on the turn it happens, to both readers:

- **You** see `⚠ Kenning Encounter infusion DEGRADED: <reason>` directly under
  your prompt, through the harness's `systemMessage`.
- **The trajectory** gets `[INFUSION DEGRADED — <reason> …]` as the first line
  of its context, asking it to tell you before anything else.

**Degraded** means mechanically degraded, and nothing else:
- no infusion arrived: the server was down, timed out or returned an error,
  or the hook itself failed;
- the meaning matcher could not run, so the seeds fell back to lexical
  keyword matching.

It never means "the payload wasn't relevant"; only you can judge that. When
the matcher ran and found nothing that bears on the prompt, the hook still
prints nothing: that silence is a healthy answer. The hook still exits 0 on
every path, so a degraded infusion never blocks a prompt.

The observation log (`KENNING_ENCOUNTER_INFUSE_OBSERVE_LOG`) gains two fields:
- `error_msg`: the error text, capped at 200 characters;
- `degraded`: the reason, or null.

To see it work once: stop the server container and send a prompt, and the
notice appears. Start it and send another, and it doesn't.

**If you run without a matcher key on purpose:** every prompt will now show
the lexical-fallback notice. That is accurate, because the matcher is what
selects by meaning, and the notice says so.

## Changed: the payload header names its seed channel

The payload's first line now reads `seeds: meaning-matched` when the matcher
chose the seeds. When the lexical path ran, it reads `awakened from:
<keywords>` as before. Previously a meaning-matched payload also opened with
the keywords, so a healthy header and a lexical one looked alike. This is the
one server-side change; rebuild the image to get it.

## Upgrading

1. Replace the hook script.
2. Rebuild and restart the server image to get the new header.

Nothing else changes.

As with everything here, this is described and tested only for a trajectory:
a model bound to its memory through Claude Code hooks.
