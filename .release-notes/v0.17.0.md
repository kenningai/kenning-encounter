# v0.17.0 — revisions arrive with their reasons, and the agent cannot read its own measurements

A change to how an infusion lays out a revised record, a third harness hook,
and an image that installs exactly what the lock says. No migration. Read
**Upgrading**: the hooks and the image both need a step from you.

## Changed: a revision arrives with its reason

Until now, when the matcher selected several versions of a revised claim, they
arrived in the payload as separate dated bullets in rank order. They read like
rival claims. The reason each one was revised, `revision_why`, was cut off by
the snippet budget or never reached the payload at all.

Now the neighbourhood delivers the revision itself:

- **A claim that supersedes another** (Concept, Hypothesis, Note) carries one
  line per step beneath it, ordered by its `SUPERSEDES` edges from the nearest
  predecessor back, each with the reason you wrote:

  ```
  • <current claim> (Hypothesis) [as of 2026-10-04] — <body>
      ↳ revised from <previous claim> (Hypothesis) [as of 2026-08-29] — why: …
        ↳ revised from <original claim> (Hypothesis) [as of 2026-05-30] — why: …
  ```

  Older versions the matcher also selected fold into those lines and do not
  arrive as bodies of their own. The payload gets shorter, not longer. A
  claim and its lines are kept or dropped by the budget together, never split.
- **A rebound Observation or Question** carries `↳ rebinds … — why: …` the
  same way. The earlier record keeps its body and arrives directly beneath
  the later one, ordered by the edge, because a noticing is not displaced by
  being looked at again.
- **An older version delivered without its successor** carries
  `↳ revised into …` (or `↳ rebound by …`) first under its body, so an
  outdated record never arrives looking current.
- Bare `SUPERSEDES` / `REBINDS` edge lines are dropped wherever a revision
  line replaces them.
- The infuse result's `assembly` reports `revision_absorbed` (older versions
  folded in), `revision_steps` (predecessors whose reason was delivered) and
  `revision_successors` (successors named under an older version).

A payload with nothing revised in it is unchanged, byte for byte.

The HOWTO says how to read the new lines, and why a `revision_why` is worth
writing well: it is the part of a revision that reaches the agent again.

## New: the observe guard

If you record an observation stream (`KENNING_ENCOUNTER_INFUSE_OBSERVE_LOG`)
or a shadow log, it is your measurement of the agent, and its reader is you.
An agent that reads its own measurements contaminates them. Until now that
rule was a comment in the infuse hook.

`scripts/kenning_encounter_observe_guard.py` is a `PreToolUse` hook that
enforces it. It denies any agent tool call whose path, or whose shell
command, names a protected location:

- the directories the observe and shadow logs live in, when the guard is
  wired with the same `KENNING_ENCOUNTER_INFUSE_OBSERVE_LOG` /
  `_SHADOW_LOG` values as the infuse hook;
- anything listed in `KENNING_ENCOUNTER_GUARD_PATHS` (comma-separated);
- running an observer script (`matcher_voices_report`, and anything listed
  in `KENNING_ENCOUNTER_GUARD_SCRIPTS`). Reading a script's source stays
  allowed.

The denial tells the agent to ask you for your reading instead. The guard
runs only on the agent's tool calls, so your own terminal and scripts are
untouched. It matches paths and commands, not file contents, so the agent
can still edit the guard and the docs that mention the logs. It guards
against accident, not evasion, and if it cannot read a call it allows it and
says so in a message to you.

The installer now copies three hooks, and the session-start hook's drift
check covers the guard.

## Changed: the image installs exactly what the lock says

The `Dockerfile` now installs `uv export --frozen` from `uv.lock`, then the
project with `--no-deps`. The uv binary is pinned to a version. Before this,
the image resolved its dependencies fresh at build time, so two builds of the
same tree could carry different versions, and neither had to match the lock
the tests run against.

The lock moved to current releases, past every open advisory against it,
including PyJWT 2.15.1, anyio 4.15.1, cryptography 50.0.2, mcp 1.30.0,
Starlette 1.9.0 and python-multipart 0.0.32. The transport was exercised
over real HTTP on both faces after the move.

## Upgrading

- **Rebuild the image.** `docker compose build` then
  `docker compose up -d --no-deps kenning_encounter kenning_encounter-reader`.
  The graph is untouched. An image built before this release does not match
  the lock, whatever its tag says.
- **Install the hooks again**, from this release:
  `python3 scripts/kenning_encounter_install_hooks.py`. Then add the guard
  to `settings.json` as a `PreToolUse` entry, with the same log variables
  as your infuse hook. The README shows the entry. Without the entry the
  guard is copied but does nothing.
- **Agents read a different payload layout** where records were revised.
  Nothing to configure. The HOWTO describes the new lines.
- **No new setting is required.**
